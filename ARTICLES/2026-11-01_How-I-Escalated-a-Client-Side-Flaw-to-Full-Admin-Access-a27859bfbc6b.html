How I Escalated a Client-Side Flaw to Full Admin Access

Author : Nilanjan Chowdhury

Prototype pollution is one of those bug classes that sounds like magic until you see it in action.

If you don’t understand JavaScript’s prototype chain, it looks impossible. But once it clicks, you realize it’s just a way to trick the language itself into giving you admin privileges.

I just spent the evening knocking out three PortSwigger labs covering Client-Side and Server-Side Prototype Pollution.

Here is how they work, and why they are so dangerous.

1. DOM XSS via an Alternative Prototype Pollution Vector

The Goal: Trigger an alert() by polluting Object.prototype via the URL.

The Vulnerability:
Many JavaScript libraries parse the URL query string and merge it into a configuration object without sanitizing the keys. If you can pass __proto__ as a key, you modify the base Object for every object in the page.

The Exploit:
I used the URL search parameter to inject a malicious property.

text

?__proto__[transport_url]=data:,alert(1)

Why it works:
The application had a script that took the URL parameters and merged them into a config object. Because I used __proto__, I didn't just add a property to that specific object—I added it to the global Object.prototype. Later in the code, a function read the transport_url to load a script, and instead of a safe URL, it executed my data: URI payload.

The Fix:

  • Never merge user-controlled objects into application state.
  • Use Object.create(null) to create objects without a prototype.
  • Sanitize keys like __proto__, constructor, and prototype.

2. Client-Side Prototype Pollution via Flawed Sanitization

The Goal: Bypass a WAF or sanitizer that is trying to block __proto__.

The Vulnerability:
The developers knew about prototype pollution, so they wrote a sanitizer to strip out __proto__. But they didn't account for alternative syntax.

The Exploit:
Instead of __proto__, I used constructor[prototype].

text

?__proto__[polluted]=true&constructor[prototype][polluted]=true

Why it works:
In JavaScript, Object.constructor.prototype is the exact same thing as Object.__proto__. By nesting the payload, I tricked the sanitizer into ignoring the constructor key, but the underlying JavaScript engine still processed it, polluting the global prototype.

The Fix:

  • Don’t use regex-based blocklists for security.
  • If you use JSON.parse(), use a reviver function to strictly filter out dangerous keys.
  • Use a library like lodash and make sure it is updated to the latest secure version.

3. Privilege Escalation via Server-Side Prototype Pollution

The Goal: Escalate your privileges to access the admin panel.

The Vulnerability:
This is the scariest one. This isn’t just in the browser anymore. The backend (likely Node.js) was using a vulnerable library to merge JSON data from a user profile update.

The Exploit:
I intercepted the POST /my-account/change-email request. I changed the JSON body to include the __proto__ payload:

json

{
  "__proto__": {
    "isAdmin": true
  }
}

Why it works:
When the Node.js backend received this JSON, it merged it into the user’s session object. Because isAdmin didn't exist on the user object, the application fell back to the prototype chain. Since I had polluted the global prototype to set isAdmin: true, the backend now thought every user was an admin.

I refreshed the page, navigated to /admin, and deleted the user wiener.

The Fix:

  • Use a secure JSON merge function.
  • Reject requests that contain __proto__ or constructor in the body.
  • In Node.js, use the --disable-proto=throw flag to completely disable prototype access.

The Takeaway

Prototype pollution is a monster. It bridges the gap between client-side XSS and server-side RCE.
