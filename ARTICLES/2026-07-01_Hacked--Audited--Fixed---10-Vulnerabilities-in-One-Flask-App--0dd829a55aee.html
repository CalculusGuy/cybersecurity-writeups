Hacked, Audited, Fixed — 10 Vulnerabilities in One Flask App.

Author: Nilanjan Chowdhury

Some nights you just want to break something.

Task 3 of my cybersecurity internship was a secure code review — audit a vulnerable Flask application, find every weakness, prove it, then fix it.

Simple brief. Interesting execution.

Here’s the story.

The Target

A Python Flask web app with 10 intentional vulnerabilities hidden inside.

I cloned it, fired it up, and immediately noticed the first red flag — debug mode was ON in production.

Not a great start for the app. A great start for me.

The Hunt

I approached it the way any attacker would — start at the entry points, work inward.

🔴 #1 — SQL Injection (Critical)

The login page fell first.

The app was building database queries by directly joining user input into strings. No parameterization. No sanitization. Just raw trust.

One manipulation of the username field:

username: admin' --
password: anything

Response:

json

{"message": "Welcome admin' --", "status": "success"}

Inside. No password needed.

The '-- comments out the rest of the SQL query — the password check never runs. This is SQL Injection 101. And it still breaks real apps in 2026.

The fix: Parameterized queries. Always.

🔴 #2 — Command Injection (Critical — RCE as Root)

There was a /ping endpoint that ran system commands based on user input.

The problem — it trusted that input completely.

/ping?host=127.0.x.x;id

Response:

uid=0(root) gid=0(root) groups=0(root)

Root. One semicolon. That’s it.

When you pass user input directly to a shell, the shell interprets everything — semicolons, pipes, backticks. The attacker isn’t just pinging anymore. They’re running whatever they want.

The fix: shell=False. Strict input validation. Never trust user-controlled data in system calls.

🔴 #3 — Broken Access Control (High)

The ad**n panel had no door.

GET /ad**n

json

{
  "all_users": [
    [1, "admin", "password", "admin@example.com"],
    [2, "alice", "1234", "alice@example.com"]
  ]
}

No login. No token. No check. Plaintext passwords. Full user database.

Anyone who typed /admin was in.

The fix: @login_required + @admin_required decorators. Every sensitive route needs a guard.

🔴 #4 — Insecure Deserialization (Critical — The Most Dangerous One)

This is the one that made me stop and think.

The /profile endpoint accepted user-supplied data, decoded it, and passed it directly to Python's pickle.loads().

Here’s why that’s catastrophic.

When Python deserializes a pickle object, it executes the __reduce__ method of that object. If you control the object being deserialized — you control what gets executed.

python

class Exploit:
    def __reduce__(self):
        return (subprocess.check_output, (["id"],))

Send that as a base64-encoded pickle to the profile endpoint.

Response:

json

{"profile": "b'uid=0(root) gid=0(root) groups=0(root)\n'"}

Remote Code Execution. As root. Through a profile page.

This isn’t theoretical. This is what untrusted deserialization looks like when someone actually uses it.

The fix: Never deserialize untrusted data with pickle. Use JSON.

What This Actually Taught Me

Vulnerabilities don’t exist in isolation.

The debug endpoint exposed the secret key. The secret key could forge session tokens. Forged tokens bypassed the broken access control. The admin panel then leaked plaintext passwords.

One chain. Full compromise.

That’s the real lesson — security isn’t about patching individual holes. It’s about understanding how weaknesses connect and what an attacker can build from them.

Every endpoint. Every input. Every error message tells a story.

Your job is to read it before someone else does.
