SQL Injection — How I Extracted a Full Database. #CyberSecurity

Author: Nilanjan Chowdhury

My Website: https://calculusguy.github.io/nilanjanchowdhury.github.io/

It started with a single input field.

Nothing fancy — just a product filter:

/filter?category=Gifts

But something about it felt… testable.

I intercepted the request in Burp Suite and typed the most basic payload I knew:

' OR 1=1--

The page responded normally — but too normally.
 No errors. No crashes. Just… everything loading.

That was the first sign.

Something underneath was trusting my input more than it should.

The Moment It Became Real

I wasn’t looking at a login bypass anymore.
 I was looking at a database I could talk to.

In a controlled lab from PortSwigger, I decided to push further — not just confirm the vulnerability, but map the entire system.

That’s where enumeration begins.

Step 1 — Asking the Database What It Knows

If the database would answer my questions, I needed to ask the right ones.

I tried:

/filter?category=Gifts' UNION SELECT NULL, table_name FROM information_schema.tables--

At first, it felt like a guess.

Then the response changed.

The product listings shifted — and hidden among them were names that didn’t belong there:

users
admins

That was the moment it clicked.

I wasn’t just injecting anymore.
 I was reading the database structure.

Step 2 — Digging Deeper

If users existed, it had to store something valuable.

So I asked the next question:

/filter?category=Gifts' UNION SELECT NULL, column_name 
FROM information_schema.columns 
WHERE table_name='users'--

The response came back quietly — but clearly:

id
username
password_hash

No guessing anymore.

I knew exactly where the sensitive data lived.

Step 3 — The Dump

At this point, it wasn’t exploration — it was execution.

/filter?category=Gifts' UNION SELECT NULL, concat(username, ': ', password_hash) FROM users--

I hit send.

For a second, nothing felt different.

Then the page loaded.

And there it was:

rootmaster: $2y$10$abc...
user1: $2b$12$xyz...

No errors. No alarms. Just raw credentials sitting inside a product page.

That’s when it stopped feeling like a lab exercise.

I took the admin credentials, went to the login page, and tried them.

They worked.

What Just Happened?

This wasn’t just SQL injection.

This was database enumeration — systematically turning a small vulnerability into full control:

  • Discover tables
  • Identify columns
  • Extract real data

The reason it worked is simple:

UNION SELECT allows combining results from two queries—but only when the structure matches.
 Using NULL helped align unknown columns, making the injection valid.

From there, the database did the rest.

Why This Matters Outside a Lab

SQL injection is still one of the most dangerous vulnerabilities, consistently listed in the OWASP Top 10.

Because once this works, the attacker doesn’t just get access — they get visibility:

  • User credentials
  • Internal structures
  • Sensitive business data

Real incidents like the Sony PlayStation Network breach showed how a single weakness can expose millions.

How This Could Have Been Prevented

What made this possible wasn’t advanced hacking — it was missing fundamentals.

Parameterized queries would have stopped it completely:

cursor.execute("SELECT * FROM users WHERE id = ?", (user_id,))

Other critical defenses:

  • Restrict database permissions (don’t expose information_schema)
  • Use ORMs like SQLAlchemy
  • Deploy WAFs (as an additional layer, not the only one)

The Real Takeaway

What stayed with me wasn’t the payload.

It was the realization that:

A single unchecked input can quietly turn into full system compromise.

Enumeration is where that shift happens — 
 where “this might be vulnerable” becomes “this is fully exposed.”

One Last Note

In many real-world applications, you won’t see the data directly like this.

That’s where blind SQL injection comes in — using boolean responses or time delays to extract information silently.

Different technique. Same impact.
