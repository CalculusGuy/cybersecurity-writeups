I Broke Into Internal Networks Using SSRF — Here’s Exactly How I Did It

Author : Nilanjan Chowdhury

From localhost access to IP scanning to chaining open redirects — a complete hands-on SSRF walkthrough with real payloads.

There’s a moment in every security lab where something clicks.

For me, it was when I changed a single parameter in Burp Suite — pointed it at http://localhost/admin — and watched the server hand me a full admin panel it would never show me directly.

That moment is SSRF. And once you understand it, you start seeing it everywhere.

Who am I and why does this matter?

I’m Nilanjan — a 1st year BCA Cybersecurity student from Kolkata, India. I don’t wait for college to teach me things. I learn by breaking them.

After completing XSS and CSRF on PortSwigger, I sat down and worked through the entire SSRF section — Apprentice to Practitioner. Real payloads. Real understanding. No shortcuts.

This is that story.

First — what even is SSRF?

Server-Side Request Forgery tricks a server into making requests on your behalf — to places it should never reach.

The server becomes your proxy. Your weapon. Your way inside.

Three things make SSRF dangerous:

The server is trusted by internal systems — your browser isn’t Internal services often have zero authentication because “nothing external can reach them anyway” Cloud metadata endpoints, admin panels, and internal APIs all become accessible

If the server will fetch a URL you control — you have an SSRF vulnerability.

Now let’s break things.

Lab 1 — Basic SSRF Against Localhost Apprentice

The stock check feature fetched data from an internal URL. I intercepted it in Burp and looked at the stockApi parameter.

Original:

stockApi=http://stock.weliketoshop.net/product/check

I changed it to:

stockApi=http://localhost/admin

The server returned the full admin panel. Users listed. Delete buttons visible.

Then:

stockApi=http://localhost/admin/delete?username=carlos
Done. Carlos deleted.

Why it works: The request comes FROM the server itself. Internal systems see 127.0.0.1 and think — trusted source. No authentication needed. The server's own trust in itself becomes the vulnerability.

The fix: Whitelist allowed URLs. Validate that server-side requests only go to expected destinations. Never trust user-controlled URLs.

Lab 2 — SSRF Against Internal Network Apprentice

This one was different. No localhost. The admin panel was somewhere in the 192.168.0.X range on port 8080. I had no idea which IP.

So I used Burp Intruder to find it.

Set the payload position on the last octet:

stockApi=http://192.168.0.§1§:8080/admin

Numbers payload — 1 to 255. Started the attack. Sorted by status code. One IP returned 200. Everything else was dead.

Found it: 192.168.0.156

Then:

stockApi=http://192.168.0.156:8080/admin/delete?username=carlos

302 Found. Carlos gone.

Why it works: The server can reach the internal network. Your browser can’t. By making the server scan the range for you, you’ve turned it into an internal network reconnaissance tool.

The fix: Block server-side requests to private IP ranges. Implement network-level controls — not just application-level ones.

Lab 3 — SSRF with Blacklist Bypass Practitioner

The developer added defenses this time. Blocked 127.0.0.1. Blocked localhost. Blocked the word admin.

I bypassed all three.

Bypass 1 — IP blacklist:

http://127.1/

TCP/IP accepts 127.1 as a valid shorthand for 127.0.0.1. The blacklist didn't account for it.

Bypass 2 — Keyword blacklist: admin was blocked. So I double URL encoded the letter a:

a → %61 → %2561

Final payload:

stockApi=http://127.1/%2561dmin/delete?username=carlos

The server decoded %2561 → %61 → a AFTER the blacklist check. By the time it became admin the check was already passed.

The core lesson: Blacklists are fundamentally weak. An attacker has infinite ways to represent the same input. 127.0.0.1 = 127.1 = 2130706433 (decimal) = 0x7f000001 (hex). A developer can never block them all.

The fix: Use whitelists not blacklists. Only allow explicitly approved destinations. Reject everything else by default.

Lab 4 — SSRF via Open Redirect Chain Practitioner

This was my favourite. Not one vulnerability — two chained together.

The stock checker restricted requests to the local application only. Direct internal IP requests were blocked.

But while browsing products I noticed something. The “Next product” button had a URL like:

/product/nextProduct?path=/product?productId=2

The path parameter controlled the redirect destination. That's an open redirect.

And here’s the chain:

Stock checker only allows local URLs ✅ /product/nextProduct is a local URL ✅ But it redirects to whatever path says ✅ So I set path to the internal admin URL ✅

Payload:

stockApi=/product/nextProduct?path=http://192.168.0.12:8080/admin/delete?username=carlos

The stock checker requested a local URL — allowed. That URL redirected to the internal admin — followed automatically. Carlos deleted.

Why it works: The SSRF restriction checked the initial URL — local, trusted. It didn’t check where that URL redirected to. The open redirect became the bypass.

This is vulnerability chaining. Two medium severity issues combined into one critical impact finding. This is exactly how real-world bug bounty reports are written.

The fix: Validate redirect destinations server-side. Never use user input to construct redirect paths. Treat redirects with the same suspicion as direct URLs.

What I learned from all of this

SSRF is powerful because it abuses trust.

Internal systems trust the server. The server trusts user input. You exploit that chain.

The defenses fail in predictable ways:

Blacklists miss alternative representations Redirect validation stops at the first URL Internal networks assume they’re unreachable — until they’re not

The only robust defense is a strict whitelist of allowed destinations, network-level controls blocking private IP ranges, and treating every server-side URL fetch as a potential attack vector.

A note on Blind SSRF

Blind SSRF — where the server makes the request but you never see the response — is an equally important technique. It requires out-of-band detection tools like Burp Collaborator. That’s a topic for a future article once I get access to Burp Suite Professional.
