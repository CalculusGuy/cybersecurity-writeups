How I Exploited OS Command Injection in 10 Seconds — and How to Stop It.

I was 20 minutes into a PortSwigger lab when I typed this:
127.0.0.1; id
The response came back:
uid=0(root) gid=0(root) groups=0(root)
One semicolon. Root access. No password.

What Is OS Command Injection?

It’s exactly what it sounds like — an attacker injects operating system commands through an insecure application.

Imagine a web app that pings an IP address you provide. The command it runs looks like this:

bash

ping 8.8.8.8

Now imagine you provide:

bash

8.8.8.8; whoami

The system runs:

bash

ping 8.8.8.8; whoami

Now the attacker knows who’s running the server. That’s the beginning.

How I Found It

I first came across it during a PortSwigger lab. The application had a ping feature — harmless, simple, and completely vulnerable.

I typed:

bash

127.0.0.1; id

The server responded with:

bash

uid=0(root) gid=0(root) groups=0(root)

No authentication. No authorization. Just root access.

Why It Matters

Command injection isn’t a theoretical problem. It’s one of the most commonly found vulnerabilities in web applications. Attackers can use it to:
Read sensitive files
Execute malicious code
Compromise the entire server
In a real-world scenario, that’s game over.

How I Fixed It

During my internship at CodeAlpha, I found the same vulnerability in a Flask application. The fix was simple:

Before:

python

subprocess.check_output(f"ping -c 1 {host}", shell=True)

After:

python

subprocess.run(['ping', '-c', '1', host], shell=False)

The Lesson

OS command injection is dangerous because it’s easy to miss and easy to exploit. The solution is discipline:
Validate all user inputs
Avoid shell=True
Think like an attacker — build like a defender.

My Advice

If you’re building applications, test for command injection. If you’re testing applications, look for it everywhere.

The vulnerability is older than most developers, but it’s still around.

One semicolon is all it takes.
